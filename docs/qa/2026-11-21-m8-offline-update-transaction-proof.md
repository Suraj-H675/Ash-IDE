## Independent post-review corrections — 2026-11-21

The first fresh product/architecture and security reviews of the staged candidate identified one interrupted-rollback P1 and conditional storage API issues. The transaction now **rejects new stores during `rolling-back` until recovery completes**, **rejects JSON `null` or array metadata rather than treating it as an absent journal/pointer**, and **accepts only runtime-acquired, frozen maintenance fences** rather than arbitrary structurally compatible objects. Negative tests cover both rollback interruption boundaries, corrupted journal and pointer contents, and forged/cloned fences.

A second independent read-only final-diff product/security review found no remaining P0/P1 but raised a terminal-journal inconsistency (P2): a committed or rolled-back journal could be replaced when its active-generation pointer was missing or mismatched. **New stores now reject terminal journal/pointer disagreements before creating a replacement transaction.** An additional regression case covers missing committed pointers, missing rolled-back pointers, and rolled-back journals paired with the former candidate pointer; it verifies the old journal is unchanged and that recovery restores the prior generation when applicable. A third independent read-only product/security review of the exact corrected production-source diff found no P0/P1 and approved the fixture-only local checkpoint. After those reviews, a test-only regression was added for the first-ever generation interrupted before pointer publication and successfully retried.

Retained generation growth is bounded to **four distinct storage-slot names**, counting orphaned and interrupted entries across binary and state storage. A further generation fails closed instead of deleting rollback data. A reviewed pruning, compatible-state and disk-space budget policy is still required for production. Same-UID pathname substitution, directory-descriptor-anchored cleanup, and proof that passed roots are disposable remain unimplemented; do not use the exported fixture API on normal installations or personal data. The transaction journal is structurally validated but not authenticated against modification by another same-UID process; a forged previous-generation reference could select an unrelated retained generation. Journal authenticity and root isolation require an independently reviewed production design.

The corrected eight-file suite passed **59/59 tests**, including genuine local AppImage byte storage and the first-ever interrupted generation retry. Scoped formatting, strict lint, TypeScript and official source provenance passed in the connected workspace. The final targeted reviewers approved the unchanged production-source candidate for a fixture-only local checkpoint; the later addition was test-only with this documentation clarification.

## Code layout

The entry module exports the fixture storage operations and their public types. Policy checks, bounded inventory, process and profile fences, durable file operations, journal parsing, snapshot copying, generation staging, transaction commit, and recovery live in separate modules. Each source module stays below 300 lines. Four test suites cover fences, inventory policy, durability failures, and transaction recovery. Shared fixture setup lives in `offline-update-transaction.fixture.ts`.

The transaction uses two private roots and reuses Ash's `orcad.lock`, profile-state maintenance admission, and descriptor-pinned state recovery copy helper. Root checks require private, disjoint Linux directories but do not prove that supplied roots are disposable fixtures. This code remains unreferenced from production and must not target installed Ash or user-data roots. The fence covers participating Ash processes and profile-state readers and writers. It does not prove that provider agents, every host process, or pending writes are quiescent. It is not product installation admission.

The state policy accepts only declared fixture domains under `fixture/` and labels coverage `explicit-policy-subset`. It rejects omitted domains and excludes provider credentials, projects and worktrees, caches, legacy Orca data, and runtime session state. A test-only inspector checks each fixture schema. The tests create a disposable profile-state SQLite database with Ash's production schema helper, plus a controlled browser-state JSON fixture. This does not define complete Ash product state or prove that a candidate supports those schemas.

## Transaction and failure model

The base offline stager verifies a signed manifest, whole-artifact digest, and ELF architecture. It does not inspect the embedded SquashFS payload. It reports `candidateIdentity.state: unverified` and `activationAvailable: false` (`config/scripts/desktop-distribution/release/stage-ash-appimage.mjs`, `src/main/updater/update-preflight.ts`). The packaging input claim hashes builder inputs, not the contents finally packaged.

The storage code accepts caller-supplied artifact digests. It stores bounded, owned, single-link candidate bytes beside a schema-checked state subset in separate private roots. State inventories reject linked paths, enforce file and byte limits, hash every file, recheck the source after copying, and verify each snapshot before a generation can be selected. Inventory paths use stable code-point order so recursive traversal and snapshot verification agree on the manifest sequence. Completed files and directories are sealed read-only. The AppImage slot keeps its owner execute bit.

The journal moves through `preparing`, binary-slot durable, state-slot durable, `prepared`, pointer durable, and `committed`. The staged binary directory and AppImage file have no write bits, and Ash syncs the directory mode before rename. Directory creation, rename publication, and journal replacement use strict parent-directory `fsync`. A JSON write reports the original failure and any cleanup failure together. Successful temporary-file deletion also syncs its parent directory. A failure-injection test verifies that an injected journal `fsync` error remains visible when temporary-file deletion also fails.

Recovery verifies generation IDs from the observed artifact and state-manifest hashes. An interruption before pointer publication recovers the previous generation. An interruption after pointer publication verifies and completes the candidate generation. Rollback changes only the isolated generation pointer to the retained previous pair. It does not switch a running application or restore live data. Same-UID concurrent path-swap resistance and power-loss testing are not claimed.
