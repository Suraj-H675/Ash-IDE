# M8 offline embedded-payload attestation contract

**Disposition:** Local offline attestation tooling and diagnostic staging are implemented. This does not accept PK-05, PK-06, or RT-15 for production. The desktop updater remains inactive, `candidateIdentity.state` remains `unverified`, and staging does not install or execute an AppImage.

## Contract

`ash-appimage-embedded-payload-attestation.mjs` creates a detached, bounded Ed25519-signed statement only after `verifyAshAppImageEmbeddedIdentity` has inspected the caller-pinned AppImage and completed its final path/inode/hash check. The statement uses a fixed field order and UTF-8 JSON encoding. Verification rejects duplicate keys, alternate serialization, oversized input, invalid signatures, expired or future release manifests, wrong key fingerprints, and mismatches against the independently signed manifest or staged artifact.

The statement binds:

- the SHA-256 and release identity of the exact signed manifest bytes;
- the outer AppImage SHA-256, size, and architecture observed before and after QA;
- the signed manifest's version, architecture, asset, and package-input claim;
- the embedded `app.asar`, compiled CLI `package.json`, desktop entry, and identity sidecar SHA-256 values;
- the embedded app, desktop, and version claims, reader version/hash, SquashFS properties, and the source-commit claim.

The sidecar remains a packaging-input snapshot. A source commit is reported as matched only when it appears in the signed claim and agrees with an explicit caller pin. A null source commit is carried as missing; it is not source provenance proof. Production policy must require a non-null commit tied to an approved source/build process.

Offline staging can optionally verify a separately supplied attestation under an explicit caller-selected Ed25519 key, check its key fingerprint and expected source-commit policy, and bind it to the staged file digest. Its result is named `verified-under-caller-key`. A caller key does not become an Ash trust root, and ordinary desktop startup does not consume operator-provided keys. The CLI requires all five attestation inputs together and refuses symlinked, nonregular, or multiply linked key and evidence files.

## Post-review hardening and repeatability

The first read-only architecture and security reviews found no P0/P1 issue, but both reproduced a PEM fingerprint inconsistency: staging hashed exact PEM file bytes while the attestation library re-exported canonical PEM before hashing. The verifier now accepts an optional bounded, pinned original PEM byte buffer, checks that it parses to **the same Ed25519 public key** as the supplied `KeyObject`, and fingerprints those exact bytes. A CLI test covers a valid CRLF-encoded PEM; a negative library test covers a foreign key whose PEM-byte fingerprint otherwise matches its own supplied bytes. A caller using only the library's `KeyObject` retains the canonical-export fingerprint convention.

The security review also identified a reader-path execution race. The Linux QA reader is now opened and SHA-256 authenticated on one pinned inode, kept open throughout inspection, and launched through `/proc/self/fd/3` with that verified file descriptor passed to each child process. A genuine-image regression renames and replaces the reader pathname after verification: the child still executes the original open inode, and the final pathname-integrity check fails closed. No untrusted AppImage ELF is executed, and the signed GPL reader remains outside Git and Ash packages. **Residual limits:** an active same-UID adversary might alter the opened inode's contents; the unsandboxed native extractor and subprocess timeout are not production-safe isolation. These are explicitly QA-only defenses, not a release trust root.

For a repeatable manual QA journey, the offline attestation producer is the exported `createSignedAshAppImageEmbeddedPayloadAttestation` library function, not a separate secret-handling CLI. Supply a caller-pinned AppImage SHA-256, expected architecture, verified private QA reader path, signed manifest bytes and signature, an explicit source-commit policy, and a disposable or separately managed Ed25519 signing key. Its returned `bytes` and `signature` are the two files consumed by the existing `release:stage:appimage:offline` CLI alongside the separately pinned public key and its exact-file SHA-256. The real operator-CLI run confirmed that a genuine image succeeds and a tampered signature publishes nothing. The repository's real-fixture tests exercise this same interface without ever creating a production release key; the disposable operator example remains in the private milestone handoff.

On the corrected source, the coordinator ran **all five relevant suites with the genuine positive and negative AppImages enabled: 68/68 passed, none skipped**, including actual offline staging of the genuine AppImage. The separate actual operator CLI was rerun after the fixes: positive exit 0, tampered detached signature exit 1, no bad files published. Strict Oxlint/Oxfmt, JavaScript syntax, official pinned-Orca provenance and Git whitespace checks pass on this corrected source; the previously completed full JavaScript release build and compiled CLI/profile recovery smoke remain valid for the unchanged application runtime graph. Detailed temporary execution receipts remain private. The earlier reviewer reports apply to the pre-fix diff; focused independent post-fix review is required before local acceptance.

## Follow-up security review: private staging-directory confinement

The completed post-fix architecture review found no outstanding P0/P1/P2 issue for QA-only staging. A subsequent independently routed security review identified one P2: staging validated `stageRoot` by pathname but later created and published files through that mutable pathname. A local attacker able to rename the directory entry in a writable parent could redirect those operations after validation. That review withheld QA-only approval pending repair.

The staging operation now opens the caller-selected private directory with Linux `O_DIRECTORY | O_NOFOLLOW`, checks that the open inode and canonical pathname agree and remain owned/private, and **retains the directory descriptor** through publication and cleanup. New child creation, `.partial` writes, rename and failure cleanup use `/proc/self/fd/<fd>` paths anchored to the opened directory rather than re-resolving the caller's root. Directory synchronization uses the retained handle, and the final pathname/inode check fails closed if the stage root was replaced. The returned path is only produced after successful verification; this still cannot prevent a same-UID attacker from modifying files or paths after the function returns, and is not an authorization to install the staged artifact.

The deterministic `stage-ash-appimage-root-race.test.mjs` regression renames the checked root and substitutes a symlink immediately before the first stage directory is created. It proves staging refuses the substitution, cleans its original pinned directory and neither overwrites a sentinel file nor publishes anything inside the decoy root. On the corrected code, the six focused suites passed **69/69 with genuine AppImage cases enabled and zero skips**; the separate real-image operator CLI succeeded with a valid disposable attestation and rejected a tampered signature without publishing files. The focused independent security re-review found no reproducible P0/P1/P2 issue in the final code diff for this local QA-only scope. This is not release approval: production PK-05/PK-06/RT-15 remain NO-GO.
