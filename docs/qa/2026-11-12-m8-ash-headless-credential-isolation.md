**Date:** 2026-11-12 (Asia/Kolkata)

**Base:** clean `main` `85d6da337659c9f2c3cf85d5118b7b0c9260b5e9`; GitHub Actions [43201374684](https://github.com/Suraj-H675/Ash-IDE/actions/runs/43201374684) **succeeded**. Development branch `fix/m8-ash-owned-headless-secrets` uses an isolated worktree. This note concerns this credential-isolation milestone, **not full M8 or release acceptance**.

## Critical pre-existing security issue

The standalone Node host previously selected `ORCA_USER_DATA` or the legacy Orca user-data root by default. Its secret-store startup placed encryption keys under `~/.orca` and unconditionally invoked an inherited migration that could enumerate and re-seal legacy Jira/Linear credentials. This violated independent Ash/Orca application-data ownership. It also risked decrypting existing Ash settings with a key originally owned by Orca.

## Changes

- The direct standalone Node host now selects `ASH_USER_DATA_PATH`, or the same platform-specific Ash user-data location as the desktop CLI (`~/.config/ash-ide` on Linux with standard XDG settings; platform-appropriate Ash locations on macOS and Windows). `ORCA_USER_DATA` **cannot override** that choice. The managed CLI server launcher supplies both the new Ash selector and the legacy environment variable scoped to the same verified Ash profile, for downstream compatibility.
- Explicit paths are required to be absolute. Physical/symlink-resolved paths reject the Orca home/profile roots, aliases and descendants, unsafe parent roots, and `/` itself. Ash's secret-key directory must resolve strictly inside that selected Ash-owned profile. Linked key records (including hard links and symlinks) are refused before inherited key hardening or reading can act on them.
- Headless secrets now use an Ash-owned `ash-headless-secret-keys` directory under the Ash profile, with restricted-permission key records. Temporary profiles keep their existing disposable/unencrypted behavior, but resolve physical path identity to prevent a temporary symlink from being used for durable storage.
- For an already-populated Ash profile without an Ash-owned key, **do not create a replacement key**: the runtime remains operable while encryption/decryption is unavailable and the inherited protected-secret retention mechanism preserves existing ciphertext. The error describes `ash_headless_secret_transition_required`; the user must explicitly approve a future read-only legacy-key import before unlocking such data. Existing `os-keyring` records in the Ash key directory cannot silently read a provider keychain or migrate/re-key; an explicit deny option is applied by Ash startup.
- Removed the now-unreachable legacy Orca plaintext credential migration module, with exact pinned Orca SHA-256 recorded in `docs/provenance/ash-exclusions.json`. Read-only historical Jira/Linear credential path helpers and saved issue metadata remain, for future explicitly approved import work. Diagnostics now describe the Ash runtime and `ASH_USER_DATA_PATH` rather than advising the user to select an Orca-owned directory.
- The real packaged-Node PTY lifecycle smoke plants a _synthetic_ `~/.orca/linear-token.enc` in a disposable HOME and verifies its exact directory contents and bytes remain unchanged after runtime starts/stops. A third runtime with **only an inherited `ORCA_USER_DATA` pointing at that foreign directory** proves Ash starts instead in its own default profile. A fourth runtime uses a newly created, physically non-temporary directory with pre-existing Ash `profiles/`: it reaches `ash_runtime_ready` and authenticated CLI status while **refusing to mint an Ash-owned encryption key**. No installed Orca credentials, keys, or profile were read, copied or changed.

## Acceptance boundaries

An existing profile that previously relied on Orca's secret key has **not been silently imported or re-keyed**. Its protected settings may remain unavailable until a separately designed, explicitly user-approved migration is implemented and verified. This milestone does not claim cross-platform native keychain testing, an installed AppImage, a GUI-to-headless secret transfer, release acceptance, or removal of all other excluded Orca source. Post-integration `main` verification and the new GitHub CI result must be recorded separately.
