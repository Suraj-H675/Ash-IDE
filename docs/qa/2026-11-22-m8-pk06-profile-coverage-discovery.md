# M8 PK-06 — read-only real Ash profile storage coverage discovery

**Disposition: diagnostic milestone only. PK-05, PK-06 and RT-15 remain production NO-GO; the updater remains unavailable.** This is not a migration, snapshot, backup, rollback, compatibility certificate or maintenance-admission mechanism.

## Actual native storage observed

The standalone `config/scripts/desktop-distribution/release/inspect-ash-profile-coverage-qa.mjs` accepts an explicitly selected **private, owned, canonical Linux Ash user-data directory**. It inventories only top-level names and the immediate entries of owned profile directories; it reads **no file contents**, credentials, cookies, SQLite rows, profile identifiers or user-defined filenames into its report. Unknown names are counted, not emitted. The result cannot claim full coverage even if all observed entries are recognized. Directory inodes are opened with `O_NOFOLLOW`, inspected via pinned `/proc/self/fd` handles, and enumerated incrementally with strict bounds **before** collecting each additional name. Child metadata probes use pinned parent paths. Symlinks, hard-linked files, foreign owners, nonprivate roots, unexpected kinds, and changes during inspection fail or remain explicitly unclassified/unsafe.

Against the disposable native X11 `0.1.0 → 0.2.0 → 0.1.0` shared profile created and tested in the prior manual QA milestone, the new code observed **38 root entries** across four storage-owner groups: profile (3), browser persistent state (15), runtime/PTY/provider state (9), and cache/diagnostic state (11). Its one owned profile had **9 immediate entries**: six SQLite/recovery items (including retained backup/quarantine and live WAL/SHM), one layout/browser item and two identity/secret metadata items. The private fixture had zero unclassified or unsafe entries at either inspected level. These numbers are _observations of this disposable fixture only_, not a general state registry or completeness claim.

The resulting manifest sets `outcome: coverage-unproven`, `activationAvailable: false`, `uninspectedNestedState: true`, `liveWriterAdmissionVerified: false`, `crossVersionCompatibilityVerified: false` and `fullStateRollbackVerified: false`. Recognizing a file or owner is not evidence it is safe to discard, rewrite, copy live, or migrate. Cache/diagnostic data is explicitly **not** implicitly approved for deletion. No production startup, updater, CLI or persistence code imports this diagnostic.

## Evidence and invocation

Run `node config/scripts/desktop-distribution/release/inspect-ash-profile-coverage-qa.mjs --root ABSOLUTE_PRIVATE_ASH_USER_DATA_PATH` only for an explicitly selected root. The command prints a counts-only JSON report, never absolute paths or unknown names. Its CLI reports a generic failure on invalid roots so arbitrary sensitive filesystem paths do not leak to logs. The tests cover an owned fixture with realistic stores; SQLite backup/WAL, recovery quarantine and secret metadata names; unknown files; symlink and hard-link escape attempts; bad ownership/permissions; noncanonical roots; and private-output suppression. CI runs both the metadata inventory and explicit profile-index reconciliation regressions alongside existing native cross-version QA contract tests. It **does not** inspect live user data or run AppImages in hosted CI.

### Opt-in profile-index identity reconciliation

The same CLI accepts the explicit `--verify-profile-index` argument after the root path. **Unlike the default metadata-only mode, this mode attempts to read only `orca-profile-index.json` contents.** The index is opened from the pinned Linux directory, with `O_NOFOLLOW` and a strict **512 KiB maximum read**; the scanner reads no more than the captured descriptor size, and rejects size/identity changes. The file must be private, single-linked and unchanged during the read. `profileIndexReadAttempted` reports the opt-in attempt, while `profileIndexCompletedReadBytes` reports the verified complete count of **raw file bytes**, before strict UTF-8 decoding (or `null` if no complete stable read can be certified; `null` does not imply zero bytes touched). Invalid UTF-8 is rejected rather than silently normalized. The parsed schema version, profile ID syntax, uniqueness and active-profile membership must match the source-backed Ash index contract. The scanner compares only ID sets against actual immediate profile directories, without printing profile IDs or names. It reports `matching-ids-only`, `mismatch` (missing/orphan directory counts), or `unavailable`, without changing the root. The existing `orca-profile-index.json.bak` recovery file is accounted for separately at the root but its contents are **not** read or treated as equivalent to a validated primary index. The default mode still reads no file content. The new check does not prove complete index validity, SQLite integrity or cross-version compatibility and never makes production activation available.

The opt-in check was exercised against two separate disposable user-data roots from the native three-launch `0.1.0 → 0.2.0 → 0.1.0` test, each showing a one-profile ID match with no missing or orphaned directories. This is a **directory-identity coherence observation** under a bounded, opened index; it is not a guarantee that either executable can understand every profile data domain or that a live writer cannot modify the index after inspection. No actual user profile was scanned.

### Opt-in SQLite schema and profile-identity observation

To add a narrow read-only SQLite check, run the same command with both `--verify-profile-index --verify-profile-sqlite` after the root argument. This additional mode requires a validated index; it stops rather than inspecting profiles when the index is unavailable or contains more than 64 IDs. Each candidate `profile-state.db` must be a private, owned, single-linked regular file of no more than 64 MiB. The scanner rejects nonempty SQLite WAL **and rollback-journal** files and unsafe/oversized SHM files. A closed WAL database can retain a nonempty, private, bounded `-shm` index after checkpoint, so the SHM file alone is not evidence of pending WAL pages. A hot rollback journal cannot safely be ignored by an immutable SQLite reader and is conservatively rejected, even if it could later be recovered by a normally opened SQLite connection.

The SQLite check runs a short-lived, timeout-bounded Node `node:sqlite` worker with the **already-opened database descriptor inherited as fd 3**. It opens that descriptor in read-only, immutable mode; it never initiates journal writes or migrations. The worker observes SQLite `user_version = 3`, a bounded quick integrity check, required production column types, nullability, and the exact **one-column primary-key cardinality/identity** for each required table, plus the stored `profile_id` matched to the indexed profile directory. A composite primary key on `profile_state_meta` is rejected because it could allow duplicate `profile_id` rows. Results expose only counts grouped by status—never SQL rows, profile names, IDs, absolute paths, user settings or database contents. Both previously verified disposable native AppImage profile roots showed one schema-3/identity-matching SQLite database; neither reported a nonempty WAL or rollback journal. These are observations of the retained disposable fixtures, not a live-writer exclusion proof or a compatibility matrix across all Ash state.

`profileSqliteEvidence.state` is `schema-3-shape-and-identities-observed` only when the checked index IDs and profile directories match and every checked database meets that narrow shape/identity check. Otherwise it is `incomplete`, with counters for missing, identity mismatch, unsupported schema, unproven integrity, unsafe journal state, and unavailable data. **Even a matching report retains** `outcome: coverage-unproven`, `activationAvailable: false`, `liveWriterFenceEstablished: false`, `crossVersionCompatibilityVerified: false` and `fullStateRollbackVerified: false`. The `immutable` SQLite view is unsafe for active writers, and the tool is restricted to explicitly selected private QA fixtures, not real user profiles or production admission.

## Remaining PK-06 / RT-15 work

This inventory never traverses browser partition data, provider histories, terminal state, encrypted secrets, extension storage or the contents of recovery snapshots. Pinned directory descriptors prevent pathname-to-symlink substitution from redirecting an opened scan, but they do **not** freeze same-UID in-place mutations. It does not compare the profile index against every profile, authenticate file contents, prove cross-time live filesystem stability, freeze writers, inspect schema compatibility, or prove executable rollback. A future complete policy needs explicit state ownership and compatibility for every retained/mutable domain; tested cross-version migrations, full backups and restoration, crash-safe recovery, and an exclusive runtime/provider/PTY/write maintenance fence. Until then, **all production update gates remain closed**.
